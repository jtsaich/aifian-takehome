## 1. 核心問題與關鍵假設

老闆開口要的是會員 App，但現場看到的問題在喜餅訂單：喜餅約占營收四成，上一季有 3 筆日期或數量記錯，造成退款和負評；中央廚房要等六家門市各自把 Excel 用 LINE 傳來，才知道下週要做多少。

我判斷的核心問題是：**訂單從門市到廚房這一段，沒有任何人或系統在檢查，也沒有一份大家都信得過的總數。** 每家門市的 Excel 格式不同，改單時只是改掉 Excel 裡的一格，廚房不會知道哪一張單在什麼時間被誰改過。錯誤要到客人取貨時才會被發現。

會員是終點，排在第 4–6 週。老闆想要的會員做得出來，但會員要有資料才有用，資料有兩個來源：喜餅訂單和門市的 POS 消費。喜餅訂單現在散在六份格式不同的 Excel，POS 只記日期、門市、品項、數量、金額，記不到是哪位客人買的。所以第一週先做門市內部的喜餅訂單管理，把訂單和客人電話整理成一份可用的資料；這一步本身就解決退款和廚房等 Excel 的問題，也是會員的底。會員要接 POS，需要外包廠商改東西，廠商排期一個月起跳，所以需求第一週就提出（見第 4、5 節）。

關鍵假設（都還沒跟客戶確認，第一次開會要驗證）：

| # | 假設 | 如果不成立 |
|---|---|---|
| A1 | 門市已經在用 LINE 群組傳 Excel 給廚房 | 群組設計要重談，見第 6 節 |
| A2 | 3 筆事故錯在門市記錄或改單，而不是廚房或交付 | 檢查的重點要移到別的環節 |
| A3 | 門市人員能接受統一範本，但不能接受新系統 | 如果能接受，可以考慮表單輸入 |
| A4 | 廚房彙總的各門市列依接單門市分；送到哪家店由廚房照現有流程決定，跨店取貨或宅配由門市寫在備註 | 跨店取貨很多、廚房需要系統告訴它送到哪家店時，範本才加「取貨門市」欄 |
| A5 | 現有群組裡沒有別的 bot | 一個群組只能有一個 bot，見第 6 節 |
| A6 | 每月喜餅訂單在數十到一百多筆之間 | 量大很多時，要重看託管規格和審核人力 |
| A7 | 總部有人專門彙整各店 Excel、再交給廚房，這件事每週花掉固定的工時 | 主指標要改；沒有這個人的話，看廚房拿到數量的時間點 |

## 2. MVP 怎麼切、刻意不做什麼

設計原則是**門市不學新系統，改動都放在門市看不到的一側。** 門市人員多半是資深員工，從紙筆走到 Excel 已經花了很久，再換一套工具就是新的出錯來源。

現況和導入後的流程對照（泳道圖）見 `docs/workflow.md`。

門市只改兩件事：

1. 改用統一範本。一列是一個品項，用門市自己的單號把同一張單串起來。欄位順序可以不同，欄名接受同義寫法。
2. 把中央廚房的 LINE 官方帳號（OA）加進現有群組。門市傳檔的對象不變。

後端做的事：

- **收檔就回覆。** 每一份檔案都在群組裡回覆：哪家門市的檔案、新單幾張、修改幾筆、哪一列有什麼問題。reply 不計費。
- **修改自動分類。** 同一個單號再出現且內容不同，系統自動判斷是追加、減量、改取貨日、取消、資料更正，或疑似單號重複使用（兩位店員把同一個號碼給了兩位客人）。總部不用自己對照新舊兩版。
- **修改截止點。** 影響生產的修改，在取貨日前 7 天以前直接生效；之後變成「待確認」，等總部人員在網頁上確認或退回。天數總部可以調。
- **總表、廚房彙總、待處理、客人資料四個網頁**，都能下載 Excel。廚房彙總只看取貨日。
- **歷史資料匯入。** 各店舊 Excel 由我們逐份轉成範本格式後匯入，只建客人資料。

刻意不做的事：

| 不做 | 原因 |
|---|---|
| 門市改用表單或 App | 違反「門市不學新系統」，而且新工具本身會帶來新的錯 |
| 把每次上傳當成門市的全店快照 | 門市每天傳的是一批訂單。檔案裡少了一列，可能是開了新檔、刪了舊月份，不能當成取消。取消要在範本上明確標記 |
| 用電話猜是哪一張單 | 同一位客人可能有好幾張單，猜錯正好造成我們要解決的錯。單號一律必填，靠編號訂購單補救 |
| 品項模糊比對 | 猜錯的品項會直接錯進廚房彙總。改用總部維護的別名清單 |
| 系統推算生產日 | 哪一款要提前幾天做，是廚房的專業判斷 |
| push 通知 | 依群組人數計費，見第 3 節 |
| POS 對帳 | POS 分不出喜餅取貨和現場購買，對帳數字不可靠。第一週向廠商提出另開品項，改好後第 4–5 週再做 |
| 會員、行銷訊息 | 第一週不做，排在第 4–6 週。會員需要的訂單資料和 POS 改動，第一週就開始準備；客人電話拿去行銷需要客人另外同意 |
| 宅配、跨店取貨 | 照現有流程 |
| AI 解析 | 同樣的輸入要得到同樣的結果，每一筆都能追溯 |

## 3. 技術選型：自建，還是用現成工具

### 先排除的限制

這幾條 LINE 平台的事實決定了大部分選項：

- OA 預設不能加入群組，要在 LINE Developers Console 打開設定；**一個群組同時只能有一個 OA。**
- bot 收得到群組裡傳的檔案，但檔案內容 LINE 不保證保存多久，收到就要下載。
- bot **不能傳檔案**，只能傳文字、圖片、Flex 等，Excel 只能給下載連結。
- reply 不計入訊息額度，但收到事件後 1 分鐘內要用、只能用一次。push 計入額度，**以收訊人數計算**：push 一則到 8 人的群組算 8 則。
- 台灣 OA 方案：輕用量每月 0 元、免費 200 則；中用量 2026-11-01 起每月 1,000 元、3,000 則；高用量每月 1,400 元、6,000 則，超出另計。

所以不論用哪種工具，「群組收檔、驗證、回覆」這一段都要有一個能接 LINE webhook 的程式。現成工具只能取代後半段的資料管理。

### 比較

| 選項 | 費用（查證時） | 能不能直接接群組傳來的 xlsx | 修改規則與截止點 | 主要問題 |
|---|---|---|---|---|
| **Ragic** | 免費版 3 張表單各 1,000 筆；簡易版 USD 5／人／月；專業版 USD 19／人／月；無限使用者版 USD 499／月 | 未查證，沒找到原生功能，推測要另外串接 | 要自己用公式或腳本做 | Excel 匯入和修改紀錄都有，資料可放台灣；但群組收檔、自動分類修改、待確認流程還是要自己寫 |
| **Google Sheets＋Apps Script** | 免費；Consumer 帳號觸發器每天合計 90 分鐘 | Apps Script 的 `doPost` 讀不到 request header，無法驗證 LINE 的簽章；回應是 302 轉址，LINE 會不會當成失敗，未查證 | 寫在 Apps Script 裡 | 驗不了簽章，任何人都能偽造請求；試算表能被直接編輯，稽核紀錄不可靠 |
| **Airtable** | Free 每個 base 1,000 筆、每月 100 次 automation、2 週修改紀錄；Team USD 20–24／人／月 | 沒有原生功能 | 自動化可以做一部分 | 免費版的筆數與 automation 次數對喜餅訂單偏緊；依人數計費 |
| **WiXtar 星益欣 烘焙 POS** | 月租訂閱，依店數與模組調整，**未公開價格** | 不適用 | 有「半客製喜餅與禮盒管理」：門市接單轉工廠生產、分批出貨、進度查詢 | 功能最貼近，但等於換掉現有 POS，是大決策；客戶已經有外包 POS |
| **自建**（Python＋Postgres，Cloud Run＋Neon） | Cloud Run 每月免費 18 萬 vCPU-秒、200 萬次請求，閒置不收費；Neon 免費方案 1 GB 儲存，閒置 5 分鐘後暫停 | 可以，照官方要求驗簽、去重 | 完全照需求寫 | 要有人維護 |

### 結論

**MVP 自建。** 群組收檔和回覆這一段無論如何都要寫程式；修改分類、截止點、重複送來的修改這些規則，正是這次要解決的問題核心，放進試算表或表單工具裡反而更難測試。以這個規模，託管費用在免費額度內，LINE 只用 reply，OA 用免費的輕用量方案就夠。

自建的代價是維護。降低這個代價的做法：全部資料隨時可以下載 Excel，萬一不再維護，客戶手上的資料不會被鎖住。

**WiXtar 要認真看。** 如果客戶本來就打算換 POS，或現在的外包廠商合作不順，WiXtar 這類烘焙專用 POS 可能比自建加外包 POS 更划算。要先問到報價。

## 4. 接下來 2–6 週

| 週 | 做什麼 | 要學到什麼 |
|---|---|---|
| 1 | 開始前先訪談：總部負責彙整各店 Excel、再交給廚房的同仁，廚房，試用門市店長；逐筆追上一季 3 筆事故。做出門市喜餅訂單管理的試用版（範本、編號訂購單、OA 進群組、總表與廚房彙總），一家門市試用、新舊並行，試用版直接拿回給總部彙整的同仁和廚房用。**向 POS 廠商提出會員需要的修改**（結帳時記下客人電話或 LINE 會員條碼、每晚 CSV 改成逐筆交易並帶收據號與時間、另開「喜餅訂單取貨」品項並填單號、CSV 自動放到固定資料夾），請廠商區分調設定或改功能，改功能的報價排期 | 總部同仁現在怎麼彙整、每週花多少時間；試用版能不能取代他們的做法；那 3 筆錯在哪一步；廠商各項要多久、多少錢 |
| 2–3 | 依訪談和試用調整範本、回覆文字和截止點；擴到六家門市；匯入歷史資料，整理成客人資料；開始記錄 near-miss | 總部彙整時間有沒有下降；待確認一週幾筆，總部處理得來嗎；按時上傳比例 |
| 4–5 | **會員同意加入**：取貨時請客人掃 QR code 加 OA 好友或領 LINE 會員卡，客人同意後才從客人資料變成會員。廠商改好的話，開始讀 POS 每晚 CSV：喜餅取貨品項和訂單對帳，帶會員識別的現場消費掛到同一位會員 | 取貨時的加入率；現場消費有多少比例帶得到會員識別 |
| 6 | 跟老闆一起看會員數、回購和門市推廣的負擔，決定 LINE 會員卡夠不夠用，還是要開發會員 App | App 要解決的是會員卡做不到的哪件事 |

會員的預設做法（門市怎麼認會員、點數與效期、LINE 與簡訊的成本、行銷在各階段能追的數字、個資與點數的法規預設、第 6 週要不要做 App 的判斷條件）見 `docs/membership.md`。

會員要接 POS 消費紀錄時，如果點數不需要即時更新，就不必請廠商開 API：每天匯出 CSV，我們排程對應到會員。但「這筆交易是哪位會員」還是要 POS 記下某種會員識別，這要跟廠商談。

這張表會依前面幾週學到的東西調整。例如第 2 週待確認多到總部處理不來，就先回頭調整截止點，不往下擴店。

## 5. 第一次開會要問的問題

### 問老闆

**會員**

1. 為什麼想要做會員？想解決什麼問題？
2. 會員 App 要達到什麼成效，看哪個指標？
3. 如果目標是增加客源或回頭客，LINE 官方帳號加好友、LINE 會員卡這類做法會不會更直接？
4. 門市準備好推 App 了嗎？誰來引導客人下載？
5. 要不要替過去的客人建會員檔？（見下方個資問題）

**訂單流程**

6. 上一季 3 筆事故各自的經過：錯在接單、改單、傳檔、彙總還是交付？誰發現、什麼時候發現？
7. 有沒有被中途抓到、沒釀成事故的錯？大概幾筆？
8. 取貨日前幾天之後，改數量或日期要先經過總部？廚房實際上提前幾天備料？
9. 現在傳檔的 LINE 群組長什麼樣子（一個大群組，還是每店一個）？**群組裡是不是已經有別的 bot？** 一個群組只能有一個 bot，有的話要另開群組。
10. 可以接受官方帳號在群組裡公開指出門市的錯嗎？
11. 各門市有沒有編號的紙本訂購單？有沒有還在用手寫的？
12. 每月喜餅訂單量、平均盒數、客人多久前下單、多少比例會改單？

**個資**

13. 客人的電話當初是為了完成訂單才留的。拿來建會員或發行銷訊息，屬於個資法說的「特定目的外利用」，原則上要客人另外同意。這部分需要跟客戶的法務或顧問確認。【Jack 補：法律細節未查證，開會前請顧問確認】

### 問行銷部門

會員每天要用的是行銷部門，這幾題先問行銷，不先問門市。

1. 老闆說的會員 App，行銷部門理解要解決的是回頭客、新客、推播優惠，還是品牌形象？
2. 現在投哪些廣告（Meta、Google、LINE、報紙或 DM）？每月預算大概多少？看哪些數字判斷有沒有效？
3. 有了會員系統，最想知道哪一件事：哪個廣告帶來會員、會員有沒有變成回頭客，還是什麼時候發訊息最有用（例如喜餅客人之後的彌月、節慶伴手禮）？
4. 現在有沒有客人名單、LINE 好友數？發過簡訊或 EDM 嗎？
5. 過去的喜餅訂單有沒有留著客人電話、留多久？行銷有沒有在追喜餅客人之後有沒有回來買？
6. 點數、生日禮、會員等級，哪些是行銷一定要有的？由誰管點數的手動調整？

### 問 POS 廠商

1. **喜餅取貨有沒有在 POS 結帳？** 訂金和尾款怎麼記？
2. 能不能在品項設定裡另外開一個「喜餅訂單取貨」品項，跟現場購買分開？結帳時備註欄能不能填單號？這要改功能，還是只要調整設定？
3. 每晚的 CSV 能不能自動放到一個固定的共用資料夾？
4. POS 有沒有地方記下會員識別（電話、會員編號、LINE 會員條碼）？如果要加，要報價和排期嗎？
5. 每晚的 CSV 能不能改成逐筆交易，帶收據號、時間和會員識別，而不是「日期 × 門市 × 品項」的彙總？行銷要把門市消費回傳給廣告平台比對，需要逐筆資料。
6. CSV 的欄位定義和範例檔。

## 6. 如果答案是 X，我會改 Y

| 問題 | 如果答案是 | 我會改 |
|---|---|---|
| 群組裡已經有別的 bot | 有，而且不能拿掉 | 改成每家門市另開一個「門市＋OA」群組，或讓門市跟 OA 一對一傳檔；回覆就不再是全群組看得到 |
| 老闆能接受 OA 在群組公開指錯嗎 | 不能 | 群組裡只回「已收到，有 N 項待確認」，細節放網頁，由總部打電話給門市 |
| 喜餅取貨有沒有走 POS | 有，而且廠商能開獨立品項 | 第二階段加取貨對帳：同一門市、同一天、同一品項，應取貨盒數對不上就列進待處理 |
| 喜餅取貨有沒有走 POS | 沒有 | 不做 POS 對帳。改在網頁加「已取貨」勾選，由門市或總部標記 |
| 修改截止點 | 廚房固定週四鎖下週產量 | 截止點從「取貨日前 N 天」改成「每週固定時間鎖定下週」 |
| 修改截止點 | 減量在截止點後也可以接受（多做的能轉成門市現貨） | 減量不套用截止點，直接生效 |
| 3 筆事故錯在哪 | 錯在電話接單時就聽錯 | 範本檢查幫不上忙；改從 operation 下手，例如接單後用 LINE 傳確認給客人 |
| 3 筆事故錯在哪 | 錯在廚房漏看改單 | 廚房彙總加「上次以後改過的單」清單 |
| 各門市有沒有編號訂購單 | 都沒有，也不願意用 | 單號改由系統在第一次收到時配發並回覆，門市抄回 Excel（多一個步驟，但比用電話猜好） |
| 會員目的 | 想增加回頭客 | 先做 LINE 好友加會員卡，不做 App |
| 會員目的 | 想要自有通路、品牌形象 | 才評估 App，並先算清楚門市推廣的成本 |
| 要不要替過去客人建會員 | 要 | 先請顧問確認目的外利用；只能用合法的同意流程，例如發簡訊邀請客人自己加入 |
| 每月訂單量 | 遠大於一百多筆 | 重看託管規格、待確認的審核人力，以及 LINE 方案 |
| 客戶打算換 POS | 是 | 認真評估 WiXtar 這類烘焙 POS，自建的部分可能只留過渡期 |

## 7. Operation 建議

軟體只能做到一半，另一半要靠流程。

- **編號訂購單。** 每家門市都要有自己的單號制度。已有編號紙本訂購單的沿用；沒有的，我們幫門市印預先編好號的訂購單（例如「中正店 0001–0500」）。接電話時照樣手寫，鍵入 Excel 時把號碼抄過去。客人來改單時，由門市找回原本那張單。
- **傳檔規則。** 每天打烊前傳一次；接到新單或改單時可以多傳。每張單由接單的店員負責到客人取貨，名字寫在範本的「接單人」欄。
- **待確認的處理 SOP。** 指定總部負責人，每天固定時間看待處理清單。【Jack 補：處理時限，例如當天下班前】確認或退回的結果會附在門市下一次上傳的回覆裡；急件由總部人員直接打電話給門市。
- **新舊流程並行期。** 試行門市約 2 週新舊並行，舊流程照常把 Excel 給廚房，兩邊數字對得上才切換。
- **記錄 near-miss。** 在取貨前被抓到並改正的錯誤也要記：哪家門市、哪一種錯、在哪一步被抓到。這是主要成功指標的資料來源，每月檢討一次。

## 8. 成功指標與停損

- **主指標**：總部同仁每週花在彙整各店 Excel、核對訂單的時間。第一週訪談量出現在的時數，試用兩週後再量一次，同時問這份總表能不能直接交給廚房、還要不要自己再整理。
- **追蹤**：取貨前被抓到並改正的錯誤數（上一季 3 筆事故壓到 0 放在季末驗收）、廚房拿到下週數量的時間點、門市按時上傳的比例。
- **停損**：訪談發現錯在電話裡就發生了，先改接電話的流程；總部同仁和廚房用了試用版還是要自己再整理一次，先照他們的做法改、不擴店；試行兩週後門市按時上傳比例低於八成，或試行門市說範本讓接單變慢、調整後還是一樣，停下來回頭重談流程。
